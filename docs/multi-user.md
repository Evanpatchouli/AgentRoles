# 多人使用与安全边界

本文说明多人、多个 Codex、远程访问场景下，AgentRoles 当前能做什么、不能做什么，以及推荐的隔离方式。

- 适用版本：AgentRoles v0.1.0
- 最后验证：2026-11-09
- 相关文档：[MCP 接入](mcp.md) · [HTTP / CLI 接入](integrations.md) · [架构说明](architecture.md)

## 1. 结论

**AgentRoles 当前是单用户、本地优先的桌面应用，不是多租户服务。**

它支持：

- 同一个人运行多个 Codex/Claude/DSH 客户端
- 可信小团队按人、项目、客户划分不同会话
- 每个人使用独立的 AgentRoles 实例（推荐）

它不支持：

- 按用户隔离 Token 和权限
- 限制某个人只能访问某个角色或会话
- 远程多用户安全接入
- 按用户计费、配额和审计
- 让不同用户互相看不到会话、记忆和配置

## 2. 默认网络边界

AgentRoles 的外部接入服务只监听：

~~~text
127.0.0.1:<端口>
~~~

因此：

- 同一台电脑上的程序可以访问
- 其他电脑默认不能直接访问
- 别人 Codex 配置的 `http://127.0.0.1:43110` 指向的是他自己的电脑
- 需要 SSH 端口转发、内网穿透或反向代理才能远程访问

但当前没有 TLS、用户身份和按用户授权。**不建议把端口直接暴露到公网或不可信内网。**

## 3. 一个 Token，等于全部投递权限

当前只有一个共享 Bearer Token：

- 任何拿到 Token 的人都可以列出所有角色
- 可以列出所有未归档会话
- 可以向任意角色、任意会话发消息
- 没有按角色、按会话、按用户的 ACL
- 没有 Token 过期、按人撤销或按项目限制

`source` 和 `sender` 是调用方自己填写的，仅用于展示和排查，**不能作为身份认证**。

Token 还保存在 MCP 客户端配置中，能读到配置的人就能拿到 Token。

## 4. 同一会话会排队并混合上下文

运行队列按**会话**串行：

- 同一个会话同时只运行一个任务
- 后续消息进入队列，回执显示「已进入待处理队列」
- 所有消息进入同一段会话历史
- 多人共用一个会话时，模型会同时看到多个人的需求，容易混淆
- 后发消息的人只能拿到接收回执，不能通过 MCP 读取最终结果

不同会话可以并行，但会增加：

- 模型 API 并发和费用
- 模型服务的速率限制风险
- 文件、终端等技能的并发冲突
- 本地 CPU、内存和磁盘压力

## 5. 数据是共享的

以下内容都没有用户级隔离：

- 所有角色及其职责
- 所有会话和消息
- 长期记忆
- Notion Token 与数据库配置
- 工作区文件和终端工作目录
- 模型 API Key
- 外部接入 Token

只要进入同一个 AgentRoles 实例，所有人共享同一套配置和上下文。

## 6. 安全风险会被放大

共享角色如果启用了高风险技能：

- `run_command`：可在工作区执行终端命令
- 文件写入：可修改本地文件
- `http_request`：可访问本机或内网接口
- Notion 技能：可修改共享数据库

Codex 不能直接调用这些工具，但可以通过消息诱导角色调用。多人使用时，任何一个人的 Codex、脚本或被污染的输入都可能成为入口。

此外：

- 没有按用户的审计日志
- 设置页只保留最近 20 条接入记录
- 无法追踪某条消息具体由哪个真实用户发送
- 一条恶意消息可能被角色写进长期记忆，影响后续会话
- 自动提取的候选默认进入「待确认」，但高置信度偏好仍可能自动保存；多人环境建议关闭自动提取，或提高自动保存阈值

## 7. 推荐使用方式

### 场景 A：一个人，多个 Codex 进程

支持。建议：

- 每个项目使用独立会话
- Codex 调用时传 `session`
- 不要让所有项目都进入默认会话

### 场景 B：可信小团队，同一台电脑

可以使用，但要接受共享边界：

- 每个人一个会话，例如「张三」「李四」
- 项目再分会话，例如「张三 / 项目 A」
- 关闭不必要的高风险技能
- 对敏感角色关闭自动处理
- 定期轮换 Token
- 约定 source/sender 命名，但不要把它当权限

这种方式仍不能防止一个人读取或覆盖另一个人的会话。

### 场景 C：每个人独立实例（当前最推荐）

如果多人需要真正隔离：

- 每个人使用独立的 `AGENTROLES_USER_DATA`
- 使用不同端口
- 使用不同 Token
- 各自配置模型、Notion 和技能
- 各自运行自己的 AgentRoles

这是当前代码下最可靠的隔离方式。

### 场景 D：公网或不可信网络

**不建议。**

如果确实需要，至少需要额外的网关层，并清楚当前应用本身不提供：

- TLS
- 用户登录
- 按用户授权
- 配额和速率限制
- 审计和告警

更合适的方向是后续实现服务端版本，而不是直接暴露桌面版的本地端口。

## 8. 如果要正式支持多用户

需要新增：

1. 用户身份与登录
2. 每用户 Token，而不是单一共享 Token
3. 角色/会话级 ACL
4. 请求速率限制、消息配额和并发上限
5. 审计日志：用户、来源、角色、会话、动作、结果
6. 用户级 Agent、会话、记忆和密钥隔离
7. TLS 与反向代理部署方案
8. 管理后台：用户、权限、额度和告警

在这些完成之前，AgentRoles 更适合个人或完全可信的小范围协作。

## 9. 上线前检查

- [ ] 外部接入只绑定 127.0.0.1
- [ ] 没有把端口映射到公网
- [ ] Token 没有提交到 Git 或发到群聊
- [ ] 共享角色关闭了不需要的高风险技能
- [ ] 不同项目使用不同会话
- [ ] 敏感角色关闭了自动处理
- [ ] 了解 MCP 只能投递、不能读取回复
- [ ] 了解 source/sender 不是身份认证
